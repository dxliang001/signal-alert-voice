# Signal Gmail mobile pilot — design for review

Status: proposed design with security gates and bounded Codex work packets; not an implemented or connected product.

## Goal and scope

Build a small, consent-based Gmail pilot for both Android and iPhone. Busy students and professionals see two categories: Urgent / Job and Low Priority / Subscription. Low priority plays a soft tone only. Urgent plays a distinct tone followed by “Urgent message. Please check.” The critical acceptance test is the correct alert on an actual locked phone.

Support one Gmail account per user. Preserve the existing static Site, its project ID, its sample-message flow, and the 46-case regression set. Do not add SMS, modify Gmail labels, send email, or open public sign-ups in this pilot. The previous demo-only decision remains true for the current Site; real access belongs to the new mobile pilot after explicit account connection.

## Proposed architecture

Use React Native with Expo development builds for a shared mobile interface, with platform-specific notification configuration. A separate native Swift/Kotlin pair would provide more platform-specific control but require two implementations; a web-only app would not validate the native alert behavior this pilot is intended to test. The shared app is the proposed default.

Use a TypeScript backend on Firebase/Google Cloud, with Firestore for account-scoped rules and processing state, Pub/Sub for Gmail changes, scheduled jobs for recovery, and a durable notification outbox. This is a proposed hosting choice, not authorization to provision billable services. Keep the backend separate from the static Site.

Suggested repository boundaries:

- `apps/mobile`: sign-in, two inbox categories, explanations, correction controls, sound previews, pause/working hours, disconnect/delete.
- `services/mail`: Gmail authorization, change ingestion, classification, rules, outbox, and push delivery.
- `packages/classifier`: pure versioned classification logic and fixtures, shared with a generated browser-compatible copy used by the Site.
- `dist`: existing static Site remains the publishable output; preserve `.openai/hosting.json`.

First prove the two sounds with synthetic remote pushes on both platforms. Then connect Gmail. A local/browser simulation is not evidence that locked-phone alerts work.

## Account connection and mail processing

Google sign-in establishes account identity; Gmail authorization is a separate, explicit permission step. Request Gmail read-only access, not mail modification. Use a server-side authorization-code flow with state validation and supported PKCE protections. Refresh tokens stay encrypted on the backend; the app stores only its own revocable session in platform secure storage. Never put OAuth secrets in the Site or mobile bundle. Follow Google's [web-server OAuth guidance](https://developers.google.com/identity/protocols/oauth2/web-server).

For the pilot, the Gmail connection must belong to the **same Google account used to sign in to Signal**. Start consent only from an authenticated Signal session. Generate a random, single-use, short-lived OAuth `state` stored server-side and bound to that session, an exact registered redirect URI, and a nonce/PKCE verifier where supported. On callback, atomically consume the state, verify the initiating session and the granted scopes, exchange the code on the backend, and validate the returned Google ID token's signature, issuer, audience, expiry, nonce, and stable `sub` (request only `openid email` in addition to `gmail.readonly`). Compare that `sub` to the Signal sign-in `sub`; use email only for display. If the user picked another Google account, discard the grant, do not link or start a watch, and show how to restart using the matching account. Reject replayed, expired, wrong-session, and already-linked-to-another-user callbacks. See [Google's OpenID Connect guidance](https://developers.google.com/identity/openid-connect/openid-connect).

An external Google OAuth app in **Testing** status receives a refresh token that normally expires after seven days when Gmail access is requested. A one-to-two-week test must plan for reconnection after expiry, use an eligible internal Workspace configuration, or complete the applicable production verification before relying on uninterrupted access. Do not treat a five-hour Codex session or a seven-day OAuth token as a launch timeline. See [Google's refresh-token guidance](https://developers.google.com/identity/protocols/oauth2#expiration).

Connection establishes a mailbox history cursor. Existing mail may populate the inbox silently; it must not produce a backlog of voice alerts. Process new inbox messages after the connection baseline. Gmail change events notify the backend, which reads mailbox history and fetches the relevant messages. Renew watches daily, retain their expiration, and recover gaps by synchronizing history. Gmail documents expiration, delayed/dropped events, and retry behavior in its [push guide](https://developers.google.com/workspace/gmail/api/guides/push).

Verify Pub/Sub deliveries using the configured authenticated endpoint. Deduplicate classification by account plus Gmail message ID; re-delivered history events and label changes must not produce new alerts for the same message. Advance the history cursor only after durable message decisions and outbox entries exist. An expired cursor triggers bounded resynchronization, with previously seen messages excluded from new alerts. Revoked credentials mark the account disconnected and stop retries until reconnection.

Treat the Pub/Sub delivery ID and Gmail message ID as separate deduplication keys. After authenticating a callback, durably record/enqueue its history update before returning `204`. If the same authenticated callback was **already durably recorded**, return `204` without repeating work or alerts. If the transaction has not committed or a transient dependency failed, return a retryable non-success response; do not acknowledge incomplete work. Reject forged/unauthenticated callbacks. Pub/Sub retries non-success responses, so a legitimate recorded duplicate is an acknowledgment, not an error. See [Pub/Sub push acknowledgment behavior](https://docs.cloud.google.com/pubsub/docs/push).

## Classification and scam-related boundaries

Retain exact sender matching, context-aware urgency, explanations, and editable trusted contacts. A displayed `From` address or matching allowlist rule is not proof of identity. Define three domain-authentication states: `pass` only when a trustworthy **Gmail-receiver-produced**, aligned DMARC result can be established; `fail` for a trustworthy failure; and `unknown` for absent, ambiguous, forwarded, or untrusted evidence. Domain authentication is evidence about the From domain, not proof that a particular person wrote the message. Gmail `messages.get` can return message headers, but a raw `Authentication-Results` header (even one claiming a familiar `authserv-id`) is not by itself trusted. Document how the receiving infrastructure identifies its own result and removes/isolates attacker-supplied claims; validate that provenance with adversarial samples. RFC 8601 defines this trust boundary and forged-header handling; do not infer provenance merely from header text. See [RFC 8601](https://www.rfc-editor.org/rfc/rfc8601.html) and [Gmail message retrieval](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/get).

**Pilot voice rule:** an automatic Gmail voice alert requires domain-authentication `pass`, an exact user-approved sender rule, a current urgent request or a user-approved always-urgent rule, and no genuine subscription exclusion. `unknown` or `fail` goes to the reviewable low-priority column with a visible “Sender not verified for voice” explanation and **sound only**, even when the address is allowlisted or marked always urgent. An always-urgent rule bypasses the urgency-wording check only; it cannot bypass sender-authentication or subscription checks. If the Gmail integration cannot establish trustworthy receiver-produced evidence, keep all real-mail voice alerts disabled while continuing synthetic sound proofs and manual review. Do not market a DMARC pass as verification of an individual mailbox owner.

Separate explicit subscription preferences and actual list/newsletter evidence from a lone unsubscribe phrase in a footer. Genuine subscriptions remain low priority, even for an always-urgent contact. A footer alone must not automatically suppress an otherwise urgent personal/work message. Add representative, consented examples for this distinction before changing the current heuristic; update the benchmark and document the intended rule precedence.

One-time moves affect that message. Saved sender corrections affect future decisions and persist per account. Store the classifier and preference versions with each decision. The Site remains a synthetic rule playground; initially transfer rules through explicit import/export, with the app validating and saving imported settings. Do not expose real mail or account tokens in the public Site.

## Phone alerts

Bundle two short WAV clips: a soft tone, and one combined urgent tone plus spoken phrase. Use notification sounds rather than assuming background JavaScript can run text-to-speech. Expo supports bundled sounds and requires native configuration/development builds for this flow; see [notification setup](https://docs.expo.dev/push-notifications/push-notifications-setup/) and [custom sounds](https://docs.expo.dev/versions/latest/sdk/notifications/#set-custom-notification-sounds).

Android uses separate stable channels. Low Priority / Subscription must use a sound-enabled channel despite the category name: Android's low notification importance is normally silent. Users control channel behavior after creation. See [Android channels](https://developer.android.com/develop/ui/compose/notifications/channels). iOS selects the bundled clip in the notification payload; see [Apple payload keys](https://developer.apple.com/library/archive/documentation/NetworkingInternet/Conceptual/RemoteNotificationsPG/PayloadKeyReference.html).

Use Expo's push service initially, with generic category text and an opaque event ID only. No sender, subject, or message body goes into the lock-screen payload. Fetch details through the authenticated app. Track provider acceptance and errors separately from device receipt; neither proves the user heard the sound. Disable invalid device tokens.

Enable Expo's **enhanced push security** in the EAS project before any remote test push. Only the backend or a controlled test sender holds the Expo access token in secret storage and sends it as a bearer token; never bundle it in the app or expose it in logs. An Expo device push token alone must not authorize sending a spoken alert. Rotate the access token if it leaks. See [Expo's additional security guidance](https://docs.expo.dev/push-notifications/sending-notifications/#additional-security).

Use a durable outbox keyed by account/message/device and bounded retries. Remote delivery cannot promise exactly-once audible playback or strict sound serialization across operating systems. Apply a per-device burst window to reduce overlapping alerts and test the actual result; do not claim the browser audio queue solves native delivery. Working hours and pause suppress sound without losing inbox entries. Do not replay all suppressed alerts when the pause ends. Focus, silent mode, denied permissions, and device settings remain authoritative.

Give every alert an explicit `expires_at` from the Gmail provider-received time: **5 minutes for urgent voice** and **15 minutes for low-priority tone** in the pilot. If a credible receive time is unavailable, do not send an automatic voice alert. Before each send/retry, drop an outbox item whose deadline has passed while retaining the inbox entry. Set Expo `ttl` to the remaining whole seconds until that same deadline, never the full lifetime anew after a delayed retry; stop retrying at expiry. Test clock skew, delayed ingestion, offline devices, and stale retries. Expo's omitted `ttl` can otherwise leave a notification eligible for redelivery for up to four weeks. A notification already handed to Expo/APNs/FCM or displayed by the phone may not be recalled, so distinguish backend cancellation from provider/device delivery in the UI and reports. See [Expo's `ttl` and `expiration` fields](https://docs.expo.dev/push-notifications/sending-notifications/#message-request-format).

Offer instructions for the user to turn off Gmail's own notifications if they want to avoid duplicate alerts; Signal does not silently change another app's settings.

## Data, privacy, and deletion

Persist rules, encrypted grants, history cursors, message IDs, category and **reason codes without raw sender, subject, or message excerpts**, version IDs, delivery timestamps, and user corrections. Do not persist full bodies or attachments in the pilot. The inbox list fetches sender, subject, and a short preview on demand through an authenticated account-scoped backend request, with no shared or long-lived cache. Opening a message may retrieve more from Gmail on demand. If disconnected or offline, show the saved category and a clear unavailable-content state. Omit mail content from logs and analytics. Use retention limits for message metadata and diagnostic events, with deletion tests. Existing demo explanations sometimes include matched words or senders; do not persist those raw explanations unchanged.

Disconnect stops watches, disables queued delivery, revokes/deletes credentials, and removes device registrations for that account. Account deletion additionally removes saved rules and retained metadata. Enforce account ownership on every API and data access. An already delivered operating-system notification cannot be recalled reliably by disconnecting.

Google classifies Gmail read access as restricted and documents verification/security-assessment requirements. An invite-only pilot is not a blanket exemption; establish the applicable requirements before processing testers' mail. See [Gmail scopes](https://developers.google.com/workspace/gmail/api/auth/scopes).

## Security gate before private Gmail mail

This design reduces risk but cannot promise that an application will never be compromised. The current static demo has no Gmail connection or network request in the inspected source. Manually entered examples remain in page memory; saved sender rules, which can contain addresses or phone numbers, use browser `localStorage`. The demo renders message text through `textContent`. Keep using synthetic examples there; do not paste passwords, access tokens, or private mail into a public demo. Recheck the deployed version whenever the source changes.

Before connecting any personal or tester mailbox containing private mail, implement and verify all of the following. A dedicated, empty Gmail test account containing only synthetic messages may be used after the account-boundary work packet is complete.

1. **Least privilege and secrets.** Request only `gmail.readonly` as the Gmail permission, plus the minimal `openid email` identity scopes for account binding; explain that Gmail read-only can read a whole mailbox even if the app watches only `INBOX`. Store refresh tokens encrypted with a managed key and tightly scoped service identity. Keep OAuth client secrets, signing keys, Expo push access tokens, and service credentials out of GitHub, the Site, the mobile bundle, crash reports, and logs. Define key rotation and credential-revocation procedures.
2. **Account boundaries.** Authenticate every mobile API request, derive the account from the verified session rather than a client-supplied user ID, and test that one signed-in user cannot read, change, or delete another user's rules or message metadata. Default Firestore client rules to deny access and test them. Server/Admin SDKs bypass Firestore rules, so enforce account ownership in backend code and IAM as well. See [Firebase's security checklist](https://firebase.google.com/support/guides/security-checklist) and [Firestore rules testing](https://firebase.google.com/docs/firestore/security/test-rules-emulator).
3. **Trusted event sources.** Bind single-use OAuth `state` and the verified Google `sub` to the initiating Signal session; test different-account selection. Authenticate Pub/Sub push calls and verify the signed token's audience and intended service identity. Reject forged requests; acknowledge legitimate, already-durable duplicates with success and no repeated work. See [Google Cloud's authenticated push guidance](https://docs.cloud.google.com/pubsub/docs/authenticate-push-subscriptions).
4. **Content and notification privacy.** Do not send real mail to an external AI model in this pilot. Treat sender, subject, body, imported rule text, and raw authentication headers as untrusted input; render as text, never executable markup. Send only generic category wording and a random opaque event ID in push payloads. Enable authenticated Expo pushes and expire old notifications explicitly. Redact mail content and tokens from application logs, analytics, error reports, and test fixtures. Audit retained reason strings for leaked excerpts.
5. **Operational checks.** Pin and update dependencies, scan for committed secrets and known vulnerable packages, restrict cloud roles, set retention and deletion schedules, and test disconnect and account deletion. Record access and security-relevant failures without recording mail content. Document who receives a security incident report and how to revoke affected tokens. Complete Google's applicable verification and security-assessment process before a public launch.

Use dedicated test accounts and synthetic messages while these gates are being built. A consent-based private-mail pilot begins only after the security tests pass and the applicable Google access requirements have been checked; no one should enter Gmail credentials into Codex or commit them to the repository.

## Acceptance gates

1. Physical Android and iPhone: permission grant/denial, both sound previews, locked-screen and background remote alerts, foreground behavior, and a burst of mixed categories. Record OS/device/settings and whether the expected audio was actually heard.
2. Gmail: connect with matching Google `sub`, reject a different-account or replayed callback, silent initial sync, one new urgent and one low-priority message, rule correction, rule persistence on another device, duplicate/reordered events, watch renewal, expired cursor recovery, revoked access, and delayed push. Forged `Authentication-Results` and missing/failing evidence must never trigger automatic voice; an always-urgent rule cannot override that gate.
3. Privacy and delivery: no mail content in push payloads/logs, cross-account access denied, Expo push authorization required, authenticated durable Pub/Sub duplicates acknowledged without reprocessing, stale alerts dropped before send, disconnect suppresses pending backend alerts, deletion removes retained user data.
4. One-to-two-week pilot: report user-reviewed missed urgent messages and unnecessary voice alerts separately. Measure message-to-decision and decision-to-provider acceptance delays; report device-receipt delay only when observable. Do not infer audible-delivery latency from server receipts. Keep the synthetic benchmark separate from real-mail evaluation.

## Dependencies before device/live testing

The user needs access to a Google Cloud/Firebase project with required APIs and OAuth configuration, an Expo/EAS project or equivalent native build pipeline, Android push credentials, and Apple signing/push credentials. Expo's documented iOS setup requires an Apple Developer account. Use secure setup flows, not credentials pasted into chat or committed to Git. Actual Android and iPhone testers are required for the acceptance gates.

The existing Site was updated from GitHub in the prior session. Check current Sites access again before the next publish; mobile development does not depend on it. No cloud resources, mail connection, or app-store distribution are created by this design document.

## Codex work packets for a Plus usage window

These packets are intentionally small: **one packet per Codex session**, with a branch/commit, tests, and a short handoff at the end. OpenAI describes Plus limits as a shared allowance measured over a five-hour period, not five guaranteed hours of execution or a fixed number of messages. Task complexity and model choice affect usage; check the Codex usage dashboard or `/status` in the CLI. See the [official OpenAI Docs pricing and limits page](https://learn.chatgpt.com/docs/pricing). If a packet reaches the allowance or needs credentials, commit the safe partial work and report the exact blocker; resume that same packet in the next window before starting another. Keep each request narrow and avoid rebuilding the whole project in one prompt.

For each packet, tell Codex: **"Read `AGENTS.md` and `README.md`; work only on this packet in a branch; keep `dist` and `.openai/hosting.json` intact unless explicitly required; use only synthetic messages and a dedicated test account until the security gate; never paste secrets or private mail into chat or commit them; run relevant tests; commit the result; report changed files, test results, and the next blocker."** Review the diff before merging. These are target scopes, not time guarantees.

1. **Baseline and classifier extraction.** Prompt: "Make `packages/classifier` a pure TypeScript module from the current demo rules and preserve the 46 synthetic cases. Keep the Site's behavior and test entry point working. Add a regression case showing user-supplied markup is rendered inert." Done when old and new tests pass and the public Site still uses only synthetic/manual input.
2. **Mobile shell and local sounds.** Prompt: "Create `apps/mobile` with Expo development-build configuration, two bundled WAV sounds, and two buttons that schedule local notifications: soft sound only and tone plus spoken phrase. No sign-in or backend." Done when a local build can show both categories and the two notifications; document how to install a development build.
3. **Android remote audio proof.** Prompt: "Enable Expo enhanced push security before testing. Add Android notification channels and Expo push-token registration; send only synthetic generic pushes through a controlled sender with a server-held access token. Record locked-screen, foreground, denial, and mixed-burst results." Done when a physical Android phone plays the intended clips and unauthenticated push requests fail; stop for device or push credentials if unavailable.
4. **iPhone remote audio proof.** Prompt: "Use the same protected Expo project and add iOS custom-sound selection for synthetic pushes; document signing setup. Test a physical locked iPhone, Focus/silent-mode behavior, and foreground handling. Do not connect Gmail." Done when a signed device build plays each permitted sound correctly; stop if Apple signing or the device is unavailable.
5. **Backend session boundary.** Prompt: "Create a TypeScript backend skeleton with verified mobile sessions and account-scoped read/write routes for synthetic rules. Derive the user from the server-verified session; reject a client-supplied account ID. No Gmail tokens or live cloud deployment." Done when unauthenticated and cross-account route tests fail closed.
6. **Firestore and secret controls.** Prompt: "Add deny-by-default Firestore client rules, minimal service IAM documentation, local emulator tests for user A versus user B, and a no-secrets-in-repo check. Confirm server/Admin SDK routes enforce account ownership because they bypass Firestore rules." Done when both client and server isolation tests pass.
7. **Gmail OAuth connection and disconnect.** Prompt: "For one dedicated synthetic-mail test account, implement `gmail.readonly` plus `openid email` consent, a single-use session-bound state, exact redirect, validated ID-token `sub` matching Signal sign-in, encrypted backend grant storage, and disconnect. Reject different-account and replayed callbacks. Do not ingest mail or send alerts." Done when matching connect/disconnect passes and mismatched/replayed grants cannot link; document seven-day Testing-mode expiry. Provisioning and consent require the account owner's actions.
8. **Gmail baseline and new-message ingestion.** Prompt: "Add watch registration, silent initial baseline, authenticated Pub/Sub endpoint with signed-token verification, `history.list` processing, and separate delivery/message-ID deduplication for a synthetic test inbox. Commit the event before responding `204`; acknowledge already-durable duplicates without repeated work. Do not send phone alerts." Done when one new message records once, legitimate duplicates get success, forged callbacks are rejected, and transient failures retry.
9. **Gmail recovery.** Prompt: "Add daily watch renewal, expired-cursor resynchronization without an alert backlog, and revoked-token handling. Exercise delayed, duplicate, and reordered synthetic events." Done when recovery tests pass and the account disconnects cleanly after revocation.

No push delivery." Done when the existing 46 cases and new adapter cases pass without raw mail in logs or fixtures.
12. **Account-scoped inbox and corrections.** Prompt: "Display two mobile columns by fetching sender/subject/preview on demand through the authenticated backend. At send time set `ttl` to remaining life; suppress expired pending work and test delayed/offline cases." Done when synthetic flows use the correct clips, stale items do not send, and no mail content appears in payloads.
14. **Controls and deletion.** Prompt: "Add pause/working hours, suppress pending backend delivery on disconnect, stop mailbox watches, and delete retained account data.
